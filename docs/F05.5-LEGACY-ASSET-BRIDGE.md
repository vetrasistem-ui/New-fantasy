# F05.5 — PokeFans 10.98 Legacy Compatibility + Real Map Bootstrap

Status: **IN PROGRESS**

Branch: `feature/f05.5-pokefans-1098`

## Objetivo

Fazer o Fantasy Studio abrir um mapa OTBM 10.98 usando o conjunto DAT + SPR + OTB correspondente, renderizar sprites reais e permitir a primeira edição visual prática sobre conteúdo legado, sem transformar OTBM ou os formatos Tibia em contratos permanentes do Fantasy.

Primeiro alvo de compatibilidade: **PokeFans 10.98**.

```text
PokeFans 10.98
├── map .otbm
├── Tibia.dat
├── Tibia.spr
├── items.otb
├── houses XML (quando houver)
└── spawns XML (quando houver)
        ↓
Legacy Compatibility Layer
├── asset bridge DAT/SPR/OTB
└── OTBM import/open bridge
        ↓
Fantasy Asset Registry + neutral import model
        ↓
Fantasy Studio V5
```

## Regra arquitetural

- OTBM pode ser aberto/importado diretamente pelo Studio para facilitar a edição e migração.
- DAT/SPR/OTB ficam isolados na camada de compatibilidade.
- `MapDocument`/FMAP continuam sendo o modelo nativo do Fantasy.
- O runtime nativo não depende de OTBM.
- A fonte OTBM original é tratada como imutável; nunca salvar por cima dela durante importação.
- O Studio e o futuro Client consomem o mesmo `FantasyAssetRegistry` para resolução visual.
- IDs legados são metadados de proveniência, não contratos de gameplay.

## Bootstrap semântico

Quando ainda não existe uma chave Fantasy amigável, o bridge cria uma chave determinística e namespaced:

```text
legacy.pokefans1098.item.<serverId>
```

Exemplo:

```text
legacy.pokefans1098.item.4526
```

Depois, aliases/mapeamentos podem substituir gradualmente essas chaves por nomes como `terrain.grass.basic` sem alterar a origem física do sprite.

## Separação obrigatória

### Asset bridge

Responsável por:

- validar o perfil 10.98;
- ler DAT/SPR/OTB;
- resolver server id → client id → sprite(s);
- fornecer frames/sprites ao renderer por API neutra;
- cachear somente o necessário;
- usar placeholder determinístico quando algo não for resolvido;
- não persistir textura/cache no FMAP.

### Map bridge

Responsável por:

- ler OTBM somente na camada legado;
- produzir `LegacyMapImportModel` neutro;
- preservar coordenadas, floors, tiles, item ids e atributos reconhecidos;
- importar towns/houses/spawns quando presentes;
- gerar diagnóstico de desconhecidos/não suportados;
- nunca descartar silenciosamente conteúdo.

O parser OTBM não pode mutar `MapDocument` diretamente. Primeiro gera o modelo neutro; um conversor separado cria/atualiza FMAP quando solicitado.

## Perfil local

Arquivos binários não são versionados no Git. O ambiente local fornece o pack, por caminhos relativos/configuráveis, por exemplo:

```text
Game/Assets/Legacy/PokeFans1098/Tibia.dat
Game/Assets/Legacy/PokeFans1098/Tibia.spr
Game/Assets/Legacy/PokeFans1098/items.otb
Game/Imports/Legacy/PokeFans1098/global_dash.otbm
Game/Imports/Legacy/PokeFans1098/map-house.xml
Game/Imports/Legacy/PokeFans1098/map-spawn.xml
```

Os nomes físicos podem variar. O profile resolve caminhos; o código não deve hardcodar nomes fora do profile.

## Ordem de execução

1. L00 — baseline, hash do source pack, working tree limpo e CI verde.
2. L01 — `LegacyAssetProfile` + `FantasyAssetRegistry` compartilhado.
3. L02 — reader SPR 10.98 + fixture determinística mínima.
4. L03 — DAT + OTB metadata mapping e diagnóstico.
5. L04 — cache/textura SDL_Renderer3 no Studio.
6. L05 — OTBM parser → `LegacyMapImportModel` neutro.
7. L06 — houses/spawns/towns/atributos necessários.
8. L07 — abrir `global_dash.otbm` localmente sem alterar o source.
9. L08 — render do mapa real com sprites reais no Studio.
10. L09 — palette real e edição direta sobre a superfície aberta.
11. L10 — conversão transacional OTBM/import model → FMAP quando solicitada.
12. L11 — Save/Reopen FMAP, relatório de perdas/desconhecidos, regressões e evidência Windows.

## Gates do primeiro sucesso visual

- conjunto exato DAT/SPR/OTB é reconhecido e hashado;
- OTBM abre sem crash;
- coordenadas/floors são preservados;
- grounds, borders e objects visíveis usam sprites reais;
- IDs desconhecidos são contabilizados e exibidos, não descartados;
- Studio continua usando SDL3 + SDL_Renderer3 + Dear ImGui;
- source OTBM permanece byte-identical após a sessão;
- FMAP nativo não passa a serializar offsets/sprite ids físicos;
- build/testes F00–F05 continuam verdes;
- evidência real Windows registrada.

## Ferramentas do editor depois do mapa real

O estudo de referência do RME confirmou como comportamentos úteis:

- preview real do footprint do pincel;
- pincéis quadrado/circular e tamanhos;
- edição direta no viewport;
- uma operação de histórico por gesto;
- picker separado de ferramentas mutantes;
- grade, zoom, floors, XYZ e Minimap integrados.

Essas ferramentas devem ser implementadas sobre o core Fantasy e o mapa real, não copiadas do RME.
